# PBE 2027 — Modernization Plan

Status: **draft 2**, updated with review comments. Once agreed, each `- [ ]` item becomes a GitHub issue in a new **PBE 2027** project. Items tagged `#NN` already exist as issues and are moved into the project.

**Guiding principle:** keep it simple and lean. Minimal code, no extra services, lean on Bun, and stay efficient enough for Railway's smallest plan.

## Decisions so far

- **Middleware:** a small home-grown wrapper; no Hono or other framework.
- **Automatic grading** for True/False and Fill in the blank; judges can always override.
- **Fill in the blank = 1 point per blank**, set automatically. Accents are ignored when grading, and accent-only matches are flagged for judges.
- **Validation:** Zod (negligible per-request cost; see Phase 1).
- **Restarting (#26):** one run per event; no multi-run model.
- **One device per team** stays a rule, enforced by team join codes.
- **Timer:** precise across computers with minimal code, via server clock sync (Phase 2).
- **No new-event wizard.** An event home page highlights what's missing instead.
- **Dashboard:** a single list view (no card view), with tags to organize, filter and sort.
- **Suggested languages:** English, Spanish, French.
- **URLs:** the app moves to `/app`, the landing page is `/`, and the docs are `/docs`.
- **Doc screenshots:** generated by Playwright from the demo event.
- **Browsers:** the last 3 versions of each major browser.
- **Parked:** usage metrics (#16) and the MCP server. Instead, make the docs and YAML import friendly to AI agents.

- **Question types:** PG and PS merge into a single Points type.

- **Landing page and docs:** Astro + Starlight (build-time only; Bun serves the static output).

**Still open:** when to add an email provider (Phase 7). This can wait until the sign-in fixes ship.

## Phase 1 — Server middleware

Goal: make new routes easy to add, remove duplication, and centralize permissions. This is not a reinvention of Express.

```ts
// src/server/http/route.ts  (~100–150 lines total)
type Middleware = (ctx: Ctx, next: () => Promise<Response>) => Promise<Response>;
export const route = (...stack: [...Middleware[], Handler]) => (req: BunRequest) => run(stack, req);

'/api/events/:id': {
  PATCH: route(auth(), eventRole('owner', 'admin'), json(RenameEvent), async ({ event, body }) => {
    await renameEvent(event.id, body.name);
    return ok({ id: event.id, name: body.name });
  })
}
```

- [ ] `route()` with built-in error handling, plus `auth()` (with session expiry, #18), `superAdmin()`, `eventRole(...)`, `json(schema)` and `rateLimit()`.
- [ ] Service files (`src/server/services/*.ts`) shared by REST, WebSocket and admin.
- [ ] Convert routes one file at a time, starting with `events.ts`. Handlers take `(ctx) => Response`.

**Zod performance:** a few microseconds per validation versus about 1 ms for a DB query, and server-only. The real efficiency win is removing the timer's once-a-second DB writes (Phase 2).

## Phase 2 — WebSocket, timer & clear errors

### Security
- [ ] Scope `UPDATE_POINTS`, `SET_QUESTION_LOCKED` and `SET_QUESTION_GRADED` writes to the connected event (today they can reach other events).
- [ ] **Team join codes** (replace the team ID in links):
  1. Each team gets a code like `K7P-4QX` (`teams.join_code`: unique, no look-alike characters).
  2. Teams join via a link containing the code (`/join/K7P4QX`) or by typing it at `/join`.
  3. The first device to join gets a private device token and reconnects automatically after that.
  4. A second device is refused with a clear message ("already connected on another device, ask the host to release it").
  5. The host can **Release device** (the team moves computers) or create a **New code** (the old link stops working).
  The join code and the rotatable link token are one mechanism with two ways to deliver it.
- [ ] Close host/judge sockets when their session ends.
- [ ] Validate WS messages with Zod, guard `JSON.parse`, and set a max message size.

### Accurate timer with less traffic
- [ ] **Server clock sync + deadline countdowns:**
  1. On connect, the client sends 5 pings and keeps the offset from the fastest round trip (`offset = serverTime − (sent + received)/2`). It re-syncs every minute and when the tab becomes visible.
  2. The server broadcasts `endsAt` (server time) once, and each client shows `ceil((endsAt − (Date.now() + offset))/1000)`, updated locally.
  3. A server `setTimeout` locks the question at `endsAt` + grace and broadcasts the lock. Clients lock their input at the same instant, and late answers are still rejected.
  4. Pause stores the remaining ms; resume broadcasts a new `endsAt`, so every computer resumes together (#25).
  5. The server re-sends state every 5 s as a safety net.

  Precision: typically under 20–30 ms, with no drift (today's per-tick network jitter is 20–200 ms). No more per-second DB writes. About 60–80 lines changed in total.

### Clear error messages everywhere
- [ ] Connection errors with codes and specific messages, and the socket closes properly (#30).
- [ ] Per-team connection status on the Run screen (connected / reconnecting / offline, last seen).
- [ ] Reconnect forever with backoff and a "Reconnecting…" banner (today the client stops after 3 attempts).
- [ ] Queue answers while offline and resend them on reconnect.
- [ ] Error-message pass across the app (login, saving, imports, team links), paired with #10.

### Smaller fixes
- [ ] Prevent setting up the same event twice when two connections arrive at once; handle events with no languages clearly.
- [ ] Add the missing awaits; acknowledge messages after the write succeeds.
- [ ] Make `answers` the single source of truth (not copied into `runs.active_item`).
- [ ] Update `WEBSOCKET_ARCHITECTURE.md`; share message types between client and server.
- [ ] #27 Live results and an absolute max column.

## Phase 5 — Questions & data entry

**Question type audit:**

| Type | Special handling today | Finding |
|---|---|---|
| PG | none | identical to PS in code; only the label differs |
| PS | none | identical to PG |
| TF | checkbox; stored as "true"/"false" | stored per translation, though it can't differ (why #9 exists) |
| FB | one input per `__` blank | parts are comma-separated (breaks on commas); no blank count check (#14) |

`answers.auto_points_awarded` is read but never written.

- [ ] TF answer stored once on the question (removes #9).
- [ ] FB answer parts stored as a JSON array, with a live blank-count check (#14); every translation has the same number of blanks.
- [ ] FB is always 1 point per blank: the points field is hidden (shows "4 blanks · 4 points"), a migration sets existing FB questions to their blank count, and YAML import ignores `maxPoints` for FB (warns on mismatch). All 8 FB questions in the 2025 set already follow this.
- [ ] **Automatic grading** into `auto_points_awarded`:
  - TF: exact match = full points, otherwise 0.
  - FB: each blank compared to the team's language answer part; 1 point per correct blank.
  - Matching ignores case, accents, punctuation and extra spaces. Answers that only matched because accents were ignored get an "accents differ" hint for judges.
  - Points questions stay judge-graded (free text).
  - Runs as each answer is saved; recalculated if the answer key is corrected.
  - The grade screen shows an "auto" badge; judges confirm with one click or override, and the judge's score always wins. Challenges still go to judges.
- [ ] Merge PG and PS into one `Points` type: a migration converts existing questions, YAML import still accepts `PG`/`PS` as aliases, and grading guidance goes in the clarification field.
- [ ] Questions table, lean version: inline editing, Tab navigation, autosave, paste from spreadsheets. Time-boxed to 2–3 days.
- [ ] Teams: paste names in bulk, rename inline, copy or print join codes.
- [ ] Languages: one-click English / Spanish / French.
- [ ] #12 Lock question editing during an event, with a banner.
- [ ] #10 One `api()` helper with clear failure messages.
