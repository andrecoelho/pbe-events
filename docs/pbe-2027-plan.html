Decisions so far

From your comments on draft 1.

PHASE 1Server middleware

The goal: make new routes easy to add, remove duplication, and keep permission checks and shared logic in one place. This is not a reinvention of Express.

The whole thing is one function, route(), plus a handful of small middlewares. Bun's native routes and HTML imports stay as they are.

// src/server/http/route.ts  (~100–150 lines total)
type Middleware = (ctx: Ctx, next: () => Promise<Response>) => Promise<Response>;
export const route = (...stack: [...Middleware[], Handler]) => (req: BunRequest) => run(stack, req);

// usage
'/api/events/:id': {
  PATCH: route(auth(), eventRole('owner', 'admin'), json(RenameEvent), async ({ event, body }) => {
    await renameEvent(event.id, body.name);
    return ok({ id: event.id, name: body.name });
  })
}
MiddlewareWhat it does
errors()Built into route(). Catches anything thrown and returns a clear JSON error. Unexpected errors are logged as 500s with a request id.
auth()Looks up the session, checks expiry (#18), loads the user, and returns 401 otherwise.
superAdmin()Restricts the admin page to super-admins.
eventRole(...roles)Checks the user's role on the event in the URL and returns 403 otherwise.
json(schema)Parses and validates the body with Zod. Returns 400 with errors per field.
rateLimit()An in-memory limit on login, signup and password reset attempts.

The SQL then moves into small service files (src/server/services/*.ts), so the REST routes, WebSocket handlers and admin page share the same functions and permission rules. Routes are converted one file at a time, starting with events.ts, and handlers take (ctx) => Response unless you'd rather keep (req).

Answer: does Zod affect performance?

Not in a way you'd notice. Zod 4 validates a typical request body in a few microseconds, while a single Postgres query takes about a millisecond. It runs only on the server, adds nothing to what browsers download, and is only used for request bodies and WebSocket messages, not on every read.

The biggest efficiency win in this plan is elsewhere. Today the timer writes to the database once a second for every running event, and Phase 2 removes that. Together these should keep the smallest Railway plan comfortable for many simultaneous events.

PHASE 2WebSocket, timer & clear errors

Findings from reading src/server/webSocket.ts and src/frontend/components/WebSocketManager.ts, most serious first.

Security

  • security Writes can reach other events. UPDATE_POINTS, SET_QUESTION_LOCKED and SET_QUESTION_GRADED don't check that the answer or question belongs to the connected event. Fix: add an event check to every write.
  • security Team join codes, which replace the team ID in the link. This enforces one device per team for real. How it works is explained below.
  • security Sockets outlive their session. Host and judge sockets keep working after logout or expiry. Close them when their session ends.
  • security Validate WebSocket messages with the same Zod schemas as the REST routes, wrap JSON.parse in error handling, and set a maximum message size.
Answer: how team join codes work

The short join code and the rotatable link token are one mechanism. The code is the token, and you can deliver it either way.

  1. Each team gets a code like K7P-4QX, stored in a new teams.join_code column. It's 6 characters, unique, and avoids look-alikes such as 0/O and 1/I.
  2. Teams join one of two ways: they open a link that contains the code (/join/K7P4QX), or they go to /join and type the code. A typed code is handy when the host writes codes on cards or projects them.
  3. The first device to join claims the team. The server gives that browser a private device token, kept in the browser's storage, and records it on the team. From then on, that browser reconnects automatically, including after a refresh or Wi-Fi drop.
  4. A second device using the same code is refused with a clear message: "Team 4 is already connected on another device. Ask the host to release it." It no longer shows "connecting" forever.
  5. The host stays in control from the Run screen. Release device lets a team move to another computer (for example, after a laptop dies). New code invalidates a code that was shared outside the room; the old link stops working immediately.

The cost is one column and one small table (or column) for the device token, a join page, two host buttons, and a change to how the team's socket identifies itself. It's about the same size as the current team-link code it replaces.

Accurate timer with less traffic

Answer: keeping every computer on the same second

You're right that sending a start time doesn't work by itself, because every computer's clock is a little off. The fix is to measure each computer's clock difference from the server. Then every computer counts down against server time, not its own clock. This is the same trick online games use, and it's small:

  1. Sync clocks (~25 lines on the client). When it connects, the client sends 5 quick pings, and the server answers each with its current time. Each ping gives an estimate: offset = server time − (send time + receive time) / 2. The client keeps the estimate from the fastest round trip. It repeats this every minute and whenever the tab becomes visible again.
  2. Send the deadline once. When the timer starts, the server broadcasts one message with the deadline in server time, endsAt. Each computer displays ceil((endsAt − (Date.now() + offset)) / 1000) and updates it locally several times a second. So when one screen shows 23, they all do.
  3. The server stays the referee. One setTimeout on the server locks the question at endsAt plus the grace period and broadcasts the lock, and late answers are still rejected. Clients also lock their own input at the same instant, so locking looks simultaneous.
  4. Pause and resume (#25). On pause, the server stores the remaining milliseconds and broadcasts "paused at 23.4s". On resume, it computes a new endsAt and broadcasts it once. Every computer resumes from the same moment and the same number, because they all count against the same server time.
  5. Safety net. The server re-sends the current state every 5 seconds, which is cheap, so a computer that missed a message corrects itself.

Precision: today each tick arrives with whatever network delay that computer has, typically 20–200 ms, and a slow connection lags every second. With clock sync, the error is half the difference between the upload and download delay, typically under 20–30 ms, and it doesn't build up. So this is more precise than today. It also removes the once-a-second database writes and most of the messages. It's roughly 60–80 lines changed in total, with no new libraries or architecture.

  • Implement server clock sync and deadline-based countdowns as described above, and stop writing the timer to the database every tick.

Clear error messages everywhere

Your top frustration from last season was the app not saying what was wrong. This becomes its own theme, not just #30.

  • ux Connection errors say what happened and what to do (#30). The server sends an error code and closes the socket, and each screen shows a specific message: team already connected on another device, event not found, no languages set up yet, no permission for this event, or event not started.
  • ux A connection status the host can read at a glance. The Run screen shows each team as connected, reconnecting or offline, with how long ago it was last seen.
  • ux Reconnect without giving up. Today the client stops after 3 attempts (about 6 seconds) and shows an error. Instead, it keeps retrying with growing delays and shows a "Reconnecting…" banner that says the answer will be sent automatically.
  • ux Answers survive a dropped connection. Submissions made while offline are queued and resent after reconnecting. This is safe because the server already overwrites a team's previous answer.
  • ux Error-message pass across the app: review every failure path (login, saving questions, imports, team links) so each one says what went wrong and how to fix it. This pairs with #10.

  • True/False: store the answer once on the question instead of per translation. That makes #9 impossible instead of something to validate.
  • Fill in the blank: store answer parts as a list (a JSON array) instead of comma-separated text, and show a live "3 blanks, 3 answers ✓" check while editing (#14). Every translation must have the same number of blanks.

All 8 fill-in-the-blank questions in the 2025 set already follow this rule.
  • Automatic grading, using the auto_points_awarded column that already exists:
    • True/False: an exact match earns full points, anything else earns 0.
    • Fill in the blank: each blank is checked against the answer part for the team's language, and each correct blank earns 1 point, so 2 of 3 earns 2. No rounding is needed.
    • Forgiving matching: the check ignores capitals, accents, punctuation and extra spaces, so "Jerusalen" matches "Jerusalén". When a blank only matched because accents were ignored, the grade screen shows an "accents differ" hint on that answer, so a judge can take the point back with one click (e.g. papa vs papá).
    • Points questions stay graded by judges, since their answers are free text.
    • When it runs: as each answer is saved, so scores are ready the moment time is up. If an answer key is corrected afterwards, the automatic points for that question are recalculated.
    • Judges keep the final word. The grade screen shows automatic scores with an "auto" badge. A judge can confirm with one click or type a different score, and the judge's score always wins (results already prefer it). Challenges still go to judges.
  • Merge PG and PS into one Points type. A migration converts existing PG and PS questions to Points. YAML import still accepts PG and PS and treats them as Points, so old files keep working. Any grading guidance for judges goes in the existing clarification field. The type list becomes Points, True/False and Fill in the blank.

Answer: is Astro + Starlight a new dependency, and what's it built on?

Yes, it's a new dependency, but only at build time. Astro is a static-site generator built on Vite, the same kind of bundler that Bun's own bundler replaces for the app. Starlight is Astro's ready-made documentation theme, with a sidebar, search, dark mode and mobile layout. Running astro build produces plain HTML and CSS files, and the Bun server serves them as static files.

  • Nothing changes at runtime: no extra server or service on Railway, and no extra memory. It adds one build step to the Railway build command.
  • The cost: a site/ folder with its own package.json, about 200 MB of build tooling in node_modules on your machine and in CI, and a second set of conventions (.astro files, though the docs themselves are plain Markdown).
  • The alternative is the same Bun app rendering Markdown at /docs with a small Markdown library. It has the fewest dependencies, but we'd build the sidebar, search, mobile menu and table of contents ourselves, which is likely a few days of work.
  • Set up Astro + Starlight in site/, for both the landing page and the docs. The Railway build runs astro build, and the Bun server serves the output as static files at / and /docs. Docs are plain Markdown files, and in-app "Learn more" links point at their headings.
